# 方案 B：多功能小工具 PWA 前端与 APK 封装设计方案

> 文档状态：已选技术路线  
> 编写日期：2026-09-10  
> 开发方式：浏览器 F12 手机模式为主，真实安卓 APK 为最终交付物

## 1. 方案结论

项目采用 **React + TypeScript + Vite** 开发移动端 Web 前端，并加入 PWA 离线能力；最终使用 **Capacitor** 将同一份前端代码封装为安卓 APK。

```text
浏览器快速开发
    ↓
F12 手机尺寸与交互调试
    ↓
PWA 离线和本地数据验证
    ↓
Capacitor 封装安卓工程
    ↓
真实安卓手机安装 APK 验收
```

该方案不设计账号、登录、后端接口和云数据库。电费账单等业务数据只保存在浏览器 IndexedDB 或 APK 内部 WebView 的本地存储中。

## 2. 产品目标

应用是一个个人使用的可扩展工具箱：

- 首页以卡片或宫格展示已有工具。
- 每个工具拥有独立页面、业务逻辑和本地数据访问模块。
- 第一项工具为“电费分摊”。
- 后续可以增加其他生活工具，而不修改电费工具内部逻辑。
- APK 安装后能够完全离线启动和使用。
- 不接入广告、统计、登录或任何远程业务服务。

## 3. 电费分摊工具

### 3.1 输入

- 账单月份。
- 本期总电费，精确到分。
- 分摊户数，默认 2，建议限制为 1～20。
- 每一户的名称、上期读数、本期读数。
- 第一户固定为“我的电表”，不能删除。

手机页面采用纵向卡片排列，而不是将多户横向挤成多列。第一张卡片使用明显的“我的”标识。

### 3.2 计算

```text
单户用量 = 本期读数 - 上期读数
总用量 = 所有单户用量之和
单户占比 = 单户用量 / 总用量
单户费用 = 总电费 × 单户占比
```

题述示例：

```text
总电费 = 100 元
我的用量 = 200 - 100 = 100 度
另一户用量 = 150 - 50 = 100 度
总用量 = 200 度
双方各占 50%，各支付 50.00 元
```

金额禁止直接使用 JavaScript `number` 做最终分配。总金额转换为“分”的整数参与计算；小数读数使用十进制定点处理。多户取整产生的尾差使用最大余数法分配，确保各户金额之和严格等于总电费。

### 3.3 校验

- 金额和读数不能为空或为负数。
- 本期读数不能小于上期读数。
- 总用量为 0 时禁止进行比例分摊。
- 单户用量为 0 时允许计算，该户费用为 0。
- 减少户数会删除已有输入时必须确认。
- 同一月份已有账单时提示覆盖或取消；首版一个月份保留一条正式记录。
- 离开存在未保存输入的页面前提示确认。

### 3.4 历史与趋势

- 保存每次账单及其全部分摊明细快照。
- 历史记录按月份倒序展示。
- 新建下月账单时，将上月本期读数自动带入为本月上期读数。
- 数据中使用稳定的 `isOwner` 标识，而不是只依赖第一项的数组位置。
- 趋势图只读取 `isOwner = true` 的金额，默认显示最近 12 个月。

## 4. 页面与路由

```text
/
├─ /tools/electricity          新建或当前电费计算
├─ /tools/electricity/history  历史账单
├─ /tools/electricity/bill/:id 账单详情
├─ /tools/electricity/trend    我的费用趋势
└─ /settings                   设置、备份、恢复和关于
```

### 4.1 工具内部导航

工具箱外层只负责展示和选择工具，不提供全局“记录”或“趋势”入口。每个工具自行决定是否包含记录、趋势、设置等内部页面。

- 电费分摊内部使用“计算 / 记录 / 趋势”三级导航。
- 返回按钮统一回到工具箱首页。
- 其他工具可以拥有完全不同的内部栏目，不强制套用电费工具结构。
- 工具之间不共享记录列表、趋势口径或业务字段。

这种结构确保新增工具只需管理自己的页面、数据和流程，工具箱外层不会因功能增多而不断膨胀。

## 5. 前端工程结构

```text
price_calculator/
├─ src/
│  ├─ app/                    应用入口、路由、主题
│  ├─ components/             公共界面组件
│  ├─ domain/                 公共类型、金额和日期规则
│  ├─ storage/                数据库接口、Dexie、迁移
│  ├─ tools/
│  │  ├─ registry.ts          工具入口注册表
│  │  └─ electricity/         电费分摊的页面、逻辑和测试
│  └─ main.tsx
├─ public/                    图标与 PWA 静态资源
├─ android/                   Capacitor 安卓壳工程
├─ capacitor.config.ts
├─ vite.config.ts
├─ package.json
└─ package-lock.json
```

统一工具入口模型：

```ts
interface ToolEntry {
  id: string;
  title: string;
  description: string;
  icon: React.ReactNode;
  route: string;
}
```

首页根据注册表生成工具入口。新增工具时，新建 `src/tools/<tool-name>` 并添加一条注册信息即可，不设计动态下载插件系统。

## 6. 推荐技术栈

| 范围 | 选择 | 用途 |
|---|---|---|
| UI | React + TypeScript | 页面组件化与类型安全 |
| 构建 | Vite | 本地开发、热更新和生产构建 |
| 路由 | React Router | 首页、工具、历史与趋势导航 |
| 数据库 | IndexedDB + Dexie | 账单保存、查询和版本迁移 |
| PWA | Web App Manifest + Service Worker | 离线资源缓存和可安装能力 |
| APK | Capacitor | 使用相同 Web 产物生成安卓应用 |
| 单元测试 | Vitest | 计算、校验、尾差和数据逻辑 |
| 组件测试 | Testing Library | 表单和交互行为 |
| 格式检查 | ESLint + Prettier | 代码一致性 |
| 图表 | 首选 SVG 自绘简单折线图 | 需求较轻，避免过早引入大型依赖 |

不需要后端框架、服务器数据库或账号系统。

## 7. 本地数据设计

IndexedDB 设置明确的数据库名称与版本号。每个工具拥有自己的业务数据仓库和 Repository，不建立跨工具的全局记录索引。公共存储层只提供数据库连接、事务、迁移和备份等基础能力，不理解各工具的业务字段。

### `electricityBills`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | UUID 主键 |
| `billingMonth` | string | `YYYY-MM` |
| `totalAmountCents` | number | 总金额，单位分，安全整数 |
| `totalUsage` | string | 精确十进制字符串 |
| `createdAt` | string | ISO 时间 |
| `updatedAt` | string | ISO 时间 |
| `note` | string? | 可选备注 |

### `electricityShares`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | UUID 主键 |
| `billId` | string | 所属账单 |
| `position` | number | 历史显示顺序 |
| `label` | string | 当时名称快照 |
| `isOwner` | boolean | 是否为本人 |
| `previousReading` | string | 上期读数 |
| `currentReading` | string | 本期读数 |
| `usage` | string | 当期用量 |
| `allocatedAmountCents` | number | 分摊金额，单位分 |

保存主表和全部明细必须放在同一个 IndexedDB 事务中。应用代码通过 `BillRepository` 接口读写数据，不允许页面直接操作 Dexie，方便测试以及未来切换到原生 SQLite。

## 8. PWA 与 APK 的数据边界

浏览器站点和最终 APK 是两个不同的存储来源，即使代码相同，它们的 IndexedDB 数据也不会自动共享。

因此首个完整版本就必须支持：

- 将全部数据导出为带版本号的 JSON 文件。
- 从 JSON 文件校验并恢复数据。
- 导入前展示记录数量和时间范围。
- 覆盖现有数据前二次确认。
- 对数据库和备份格式分别维护版本迁移。

开发阶段积累的数据可先从浏览器导出，再在 APK 中导入。卸载 APK 通常会删除其内部数据，设置页必须明确提醒用户先备份。

## 9. 浏览器调试方式

日常开发：

```powershell
npm install
npm run dev
```

在 Chrome/Edge 打开本地地址，然后按 F12：

1. 打开设备工具栏。
2. 依次测试约 360、390、412 像素的常见手机宽度。
3. 测试竖屏、横屏、触摸滚动和较大字体。
4. 在 Application 面板检查 Manifest、Service Worker、Cache Storage 和 IndexedDB。
5. 使用 Network 面板切换 Offline，验证离线启动。

F12 能覆盖布局和大部分业务逻辑，但不能替代真实 APK 测试。系统返回键、安卓 WebView、软键盘、状态栏、文件选择器和应用生命周期必须在手机上验证。

## 10. HTTPS 注意事项

Service Worker 只能在安全来源使用：

- 电脑自身的 `http://localhost` 可以直接开发和测试。
- 手机通过 `http://电脑局域网IP:端口` 访问时，可以查看普通页面，但不能视为完整 PWA 测试。
- 手机安装 PWA 或验证 Service Worker 时，应使用 HTTPS 静态预览地址或可信本地 HTTPS 证书。

最终 APK 的 Web 文件打包在应用内部，不需要依赖线上网站才能启动。

## 11. APK 封装流程

前端功能稳定后再执行安卓封装：

1. 安装 Android Studio、JDK 17、Android SDK 和 Platform-Tools。
2. 安装 Capacitor 核心与安卓平台依赖。
3. 配置 `webDir` 指向 Vite 的 `dist` 目录。
4. 执行前端生产构建。
5. 同步 Web 产物到安卓工程。
6. 在 Android Studio 中运行调试版到真机。
7. 配置私有签名，生成 release APK。
8. 保存签名文件和密码；未来升级必须继续使用同一签名。

典型命令会在初始化项目后写入脚本，例如：

```powershell
npm run build
npx cap sync android
npx cap open android
```

安卓壳只承载本地 Web 页面和必要系统桥接，不包含远程业务网址。

## 13. 测试策略

### 自动化测试

- 两户均分 100 元应各得 50.00 元。
- 三户不能整除时，尾差分配后总和严格等于总金额。
- 零用量、小数读数、超大读数和非法倒表读数。
- IndexedDB 保存、查询、编辑、删除和迁移。
- 趋势查询只能取本人费用。
- JSON 导出后再导入能够还原相同数据。

### 浏览器验收

- 常见手机宽度下没有横向滚动或遮挡。
- 刷新、关闭标签页再打开后历史数据仍存在。
- Service Worker 更新后不会出现新旧资源混用。
- 离线状态可以启动并完成计算与保存。

### APK 真机验收

- 首次安装、离线启动和冷启动正常。
- 系统返回键行为正确。
- 数字键盘不会遮挡当前输入项或保存按钮。
- 导出和导入可以调用系统文件选择器。
- 应用被系统回收后，已保存数据不丢失。
- 使用同一签名覆盖升级后，历史数据仍存在。

## 14. 分阶段开发

### 阶段 1：前端 MVP

- 初始化 React、TypeScript、Vite 和测试环境。
- 完成工具箱首页。
- 完成电费输入、动态户数、精确计算和校验。
- 在 F12 手机模式完成响应式调试。

### 阶段 2：本地数据与 PWA

- IndexedDB、历史记录和自动带入上期读数。
- 我的费用趋势。
- Manifest、离线缓存和安装体验。
- JSON 备份与恢复。

### 阶段 3：安卓 APK

- 引入 Capacitor 和安卓工程。
- 处理状态栏、返回键、软键盘和文件接口。
- 真机测试、签名并输出 APK。

### 阶段 4：持续扩展

- 根据生活需求增加新的工具目录和首页入口。
- 仅在出现真实重复时抽取公共组件，避免提前过度抽象。

## 15. 首个完整版本验收标准

- 浏览器 F12 手机模式可以完整完成开发调试。
- 最终生成可以直接安装的安卓 APK。
- APK 不登录、不依赖服务器，断网可以完整使用。
- 用户可以设置户数并录入总电费和各户读数。
- 所有分摊金额之和始终严格等于总电费。
- 第一户固定为本人，趋势只统计本人费用。
- 历史记录在应用重启后仍然存在。
- 支持本地 JSON 导出和恢复。
- APK 升级安装不会清除历史数据。
- 关键计算、数据迁移和主要交互有自动化测试。
