## 2. 能力边界与可行性判断

| 能力 | 判断 | 产品影响 |
| --- | --- | --- |
| 用户选择一个可读文件 | 可采用系统文件选择器 | 选择器不只按 APK MIME 过滤；返回后仍校验实际内容 |
| 用户授权允许的文件夹 | 可行，但有系统目录限制 | 保存授权状态；权限失效可重新选择；不能保证整个下载目录可授权 |
| 无广泛权限自动扫描全部 QQ / 微信下载 | 不能承诺 | 不能将 `MediaStore.Files` 或下载集合当成无限制文件清单 |
| 额外授权后扫描更多共享位置 | Android 11+ 有系统能力，实际覆盖待验证 | 当前 APK 渠道可进入技术验证；仅在用户主动使用时请求 |
| 读取其他应用私有文件 | 普通第三方工具无法任意访问 | 依赖来源应用提供可读 URI 或保存至公开位置 |
| 分享 / 外部打开收到文件 | Android 支持；发送端是否提供待实测 | QQ 和微信分别验证，不写死菜单和私有路径 |
| 读取 APK 名称 / 版本 / 图标 | 可基于稳定的本地副本解析 | 失败保留未知，不凭扩展名确认 |
| 改善异常尾缀的打开体验 | 对完整、支持的 APK 可行 | 生成正确名称副本；不会修复损坏、兼容或签名问题 |
| 请求系统安装 | 需来源授权及系统安装流程 | 用户发起；返回结果可能不充分 |
| 判断任意应用是否已安装 | 受包可见性限制 | 首版不依赖全量应用清单，不把查询不到等同于未安装 |

普通作用域存储下，读取其他应用创建的下载文件有访问要求；声明图片 / 视频权限也不会使 APK 自动可读。[Android 共享存储说明](https://developer.android.com/training/data-storage/shared/media)

Android 8–9 的旧存储权限分支、Android 10 的作用域存储分支、Android 11+ 的特殊文件访问分支分别验证。共同保留系统选文件 / 合法 URI 导入；首版不为 Android 10 设计放宽存储隔离的回退方式。

安装前可检查本工具是否获准请求安装；设置返回后重新检查。当前应用以用户发起的系统安装流程为目标，不能把授予来源权限等同于同意安装每一个包。[安装来源检查接口](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls())

首版不申请 `QUERY_ALL_PACKAGES` 来补全安装统计；是否安装成功以实际安装结果为依据，包可见性未知时显示未知。[Android 包可见性](https://developer.android.com/training/package-visibility)

```text
    FileFinderFeatureDependencies.kt
    domain/                        候选规则、命名、状态、处理策略
    data/                          文件来源、索引、副本、解析与安装适配
    presentation/                  单首页查找与最近、详情、范围管理及 ViewModel
  src/test/                        领域规则、状态机和适配器测试
  src/androidTest/                 URI、存储、Room 与系统边界测试
  schemas/                        如采用 Room，保存正式 schema 与迁移依据
prototype/dist/file-finder-research/  已确认被 Git 忽略的临时调研与验证输出
```

产品文档是正式交付物，放入 `docs`；临时日志、测试 APK、个人文件样本放忽略目录，不加入 Git。`prototype/dist` 是构建输出，重要验证结论应脱敏整理到正式文档，原始证据另行备份。

应用壳仅增加注册、依赖和系统入口分发；候选识别、业务状态、索引与文件处理保留在功能模块。`core` 不反向依赖功能模块，不将 APK 安装塞进现有 `core:backup`。只在出现真实复用时抽公共文件能力。

外部 Intent 需要同时处理首次启动和已打开时的新请求，保证一次接收只消费一次。接收哪些 MIME 应依据实测收窄，优先 APK 与通用二进制类型；手动选择文件可使用全部类型。不要为了收到文件把所有网页或纯文本分享都注册成安装入口。[Android 接收分享资料](https://developer.android.com/develop/ui/compose/sharing/receive)

分享及采用 URI 的安装交付使用受控内容 URI 和临时只读授权；Provider 仅开放专用输出区域，避免暴露应用根目录。安装还需比较系统会话方案，按下文验证后冻结，不预先绑定一种实现。[Android 文件分享](https://developer.android.com/training/secure-file-sharing/share-file)

### 3.1 QQ“用其他软件打开”的优先接入设计

这是用户新增强调的首版核心入口，技术验证顺序优先于完整扫描器和索引页面。

1. **区分系统动作。** 外部打开重点验证 `ACTION_VIEW`，分享重点验证 `ACTION_SEND`；它们不是同一个匹配契约。外部可调用入口需正确声明导出状态和 `CATEGORY_DEFAULT`，并在应用内部进行输入校验。[Android Intent 匹配规则](https://developer.android.com/guide/components/intents-filters)
2. **兼容异常名称的类型信息。** 优先验证 APK 类型 `application/vnd.android.package-archive`、通用二进制 `application/octet-stream` 以及 QQ 实际传入的其他 / 缺失类型。不能假定 `.apk.1` 仍被发送端标成 APK，也不能只写一个 `.apk` 扩展名匹配规则。
3. **不依赖 URI 路径保留文件名。** `content://` 地址可能使用文档 ID；文件显示名从提供方元信息读取。匹配阶段考虑动作、URI 和 MIME，接收后再按真实内容识别，不能仅凭 URI 末尾必须是 `.apk.1` 才接受。[Android data 匹配说明](https://developer.android.com/guide/topics/manifest/data-element)
4. **扩大匹配以实测为依据。** 若目标 QQ 行为确实要求更广的文件 MIME 或无类型匹配，应分别设计限定文件 URI 的规则，并具备普通文件信息展示、另存及不支持提示；不能通过注册所有 HTTP / HTTPS 网页或伪装默认浏览器争取展示。具体过滤器组合先经目标设备验证，再冻结到开发规格。
5. **读取权限单独验证。** 收到文件 URI 后实际尝试读取；能列入选择器不代表已获读权限。正确授予的文件访问可直接用于本次导入，不应再强制申请所有文件访问。授权缺失不能靠猜真实路径绕过。
6. **单文件直达。** 使用现有应用导航承接外部输入，冷启动和新请求均直达详情并防重复消费；先识别，再由用户点安装。安装器交付和其他应用打开需避免再次解析到本工具自身。
7. **区分 QQ 自建列表。** 若入口仅推荐或限定应用、向指定包发出请求，本工具无法仅凭 Manifest 强制出现；记录实际行为并验证系统更多应用 / 分享等替代路径。不能用修改工具箱权限来声称解决发送端限制。

此处为接入规格，不是已经完成的 Manifest 变更。当前应用只声明了启动器入口，需后续开发接收、识别、文件生命周期与安装链路后一起交付，不能只加过滤器制造一个选中后无法处理的空入口。

## 4. 数据与任务设计原则

建议采用工具独立的轻量索引与记录库，具体表结构进入技术设计时确定，不修改其他工具的数据库。

| 数据对象 | 主要字段 / 含义 |
| --- | --- |
| 文件来源 | 来源 ID、类型、目录 URI / 受控路径、显示名、权限状态、上次完整扫描时间 |
| 文件索引 | 来源 ID + 来源内稳定标识、原名、大小和修改时间（可空）、首次发现时间、访问与识别状态 |
| APK 元信息 | 对应内容指纹或副本版本、包名、应用名、版本、可确定的兼容信息；不永久绑定到易变化的文件名 |
| 托管副本 | 内部文件 ID、原来源、用户显示名、实际大小、内容哈希、完整性状态、用途、最近使用、过期资格与占用状态 |
| 处理记录 | 操作 ID、不可变文件身份及副本版本、操作类型、开始 / 结束时间、结果、可确认的失败原因；系统回执关联本次操作，安装结果独立于复制结果 |
| 文件使用保护 | 副本 ID、持有者 / 操作 ID、保护原因、交付方式及会话标识、建立时间、解除依据；与处理结果独立保存 |
| 扫描任务 | 来源快照、扫描批次、任务状态、已发现数量、不可达来源、是否完整；所有类型统一枚举，展示筛选不参与完整覆盖判断 |

访问失败、文件不存在、未知大小、0 字节、用户取消分别建模。同一包名的不同版本或签名不能自动合并；索引去重先基于来源内身份，内容去重需哈希验证。跨来源去重属于 P1，不阻塞基础查找。

技术实现需满足：

- 文件枚举、复制和解析离开 UI 主线程，采用有限并发、分页 / 分批与取消机制；不同文件操作不抢占同一输出。
- 范围扫描统一登记所有普通文件的轻量元信息，再按名称筛 APK 候选并按需解析内容；不以 APK 筛选裁掉通用文件索引。搜索不计算全盘哈希或逐次加载图标。扫描到容量或执行上限标记部分完成；只有来源完整枚举才能更新覆盖标记，未匹配展示条件不代表文件消失。
- 对 URI 的未知大小、慢提供方、读取失败和权限撤回有明确处理；不把内容 URI 当成必然可转换的绝对路径。
- 输入来自其他应用，不信任路径、MIME 和容器内容；限制复制大小、解析时间、归档条目和资源解码规模。具体阈值在真实样本测量后冻结并写入开发规格，超限时显示原因，不静默漏项。
- 本地副本先完成文件写入再事务登记；不完整产物可恢复识别，正在使用的副本有占用状态，清理有一致性保证。
- 外部请求按02的F03单任务规则串行处理，至多暂挂一个不同文件请求；去重以操作消费状态和文件版本为依据，不永久按 URI 去重。授权、安装回执绑定原请求，拒绝重复安装，不能用新文件替换在途文件。
- 列表筛选在索引范围内完成，避免 UI 逐行读盘、全库逐行解析；状态变化保留稳定列表位置与滚动。
- 不执行外部文件中的代码，不自行解压整个未知归档；主流程只准备副本并请求系统处理。
- 小型模块优先复用现有运行库和平台API；新增依赖需测量正式包增量。预算为同条件APK增加不超过2 MiB，不能把整个工具箱已有离线媒体占用算作本工具新增，也不能承诺全应用因此很小。
- 单首页最近5条、全部最近最多20条；元信息裁剪不直接删除仍在使用的文件。任务暂存默认最近使用7天可清理、512 MiB软预算，受任务占用保护；大包例外与清理顺序按04落实，阈值在实测后冻结。
- 首版不引入定时清理服务或后台轮询；副本回收在进入工具或开始任务时执行。失败或未知安装结果与文件仍被读取是不同维度，副本生命周期需在技术验证中确认，不能用一到页面前台就删除的方式省空间。

### 4.1 外部交付与清理的验证项

产品规则以02的F09为准。先保护选中文件再清理；本地任务结束须关闭全部读写流。进程重启、工具箱自身更新后先恢复交付状态，不能先回收再查询。分享和安装分别验证，不能因为安装有回执就假定分享也有。

安装优先验证 `PackageInstaller.Session`：平台允许将 APK 写入独立会话，所有写入流需在 `commit` 前关闭，最终结果由回调报告；`close` 仅释放会话对象，不等于放弃安装，`abandon` 才会放弃会话及其暂存。上述是平台契约，当前机型行为尚未实测。[Android 安装会话接口](https://developer.android.com/reference/android/content/pm/PackageInstaller.Session)

设计推论：确认完整写入并不再依赖应用副本后，可解除该副本的交付读取保护，安装结果另行等待；用户确认步骤仍保留。需验证当前 targetSdk 下的回执契约、授权往返、取消、空间不足和进程恢复，核算应用副本与系统暂存同时存在的峰值，禁止把该推论写成已通过验收。

如果最终使用 URI 交付，必须证明可靠的结束依据；无法证明时保留“外部结束待确认”，按F09提供用户明确结束的出口。不能设置一个未经验证的固定超时，声称对方必然已读完。会话与 URI 方案选定后写入开发规格，未验证的备用方式不作为自动回退悄悄启用。

## 5. 后续阶段与进入条件

### 阶段 A：可达性验证

目标：确定红米 K60 上文件到底从哪里来、哪些路径真正可用。使用隔离的最小原生验证程序验证入口、读取和安装，不先建设正式索引与完整页面；这与阶段C的产品工程接入不同。临时验证产物放已忽略目录，脱敏结果写回本文档包。

交付：优先验证“QQ 的用其他软件打开 → 能选到工具箱 → 能读取 `.apk.1` → 能交给系统安装”。再按 [02 第 5 节](02-流程状态与验收清单.md#5-红米-k60-实机验证矩阵) 填写系统和软件版本，记录 QQ / 微信的实际文件名、保存位置类型、外部打开 / 分享能力、授权前后覆盖、安装往返结果；冻结首版访问模式与权限清单。

出口：QQ的“候选可选 → 读到正确文件 → 用户发起并交给系统安装”三关逐项记录，不能用手动另存绕过这条P0需求；微信至少一条有效导入路径可复现。同时选定可验证的安装交付方式，明确文件保护的建立、解除和恢复依据。QQ目标入口若被来源软件限制，明确该需求未满足，先与用户确认调整承诺，替代路径不能算原需求通过。

本机没有合适 Android 环境时可先准备样本说明、用例和验证程序，执行与结果留待设备具备后完成；不得把准备完成写成阶段A通过。无需为推进产品文档先取得手机权限。

### 阶段 B：交互原型

目标：在已确认的系统能力内，让找文件和安装路径足够短。

交付：单首页（最近 / 查找结果）、范围选择、详情、处理进度、全部最近面板、管理，以及 U01—U24 的正常 / 异常状态。已识别支持的APK统一“安装”，自动整理名称；提供模拟系统权限和安装返回，明确模拟标识；沿用项目主题。

出口：用户从查找入口和聊天入口均能理解如何完成任务；原型已覆盖失败和返回，用户确认交互。原型可以先推进通用页面，但未实测的手机能力保留标记。

### 阶段 C：技术规格与最小链路

进入条件：阶段A核心路径和交付生命周期已有证据，阶段B交互已验收；或用户明确确认基于实测结果缩减后的范围。当前仅完成文档复核，不代表已满足这些条件。

目标：将阶段A验证过的能力按现有工程习惯接入，先完成“用户选入 `.apk.1` → 解析稳定副本 → 点安装后自动整理名称 → 请求系统安装”的最小产品链路，再接QQ外部打开。

交付：数据对象与迁移方案、状态机、输入边界、资源上限、复制与取消策略、接收 Intent 的行为、安装结果判定方式。冻结单文件大小、未知大小读取上限、索引容量、枚举 / 解析超时、空间预留和超限提示；先实现单文件链路，再接 QQ / 微信入口，最后加入目录扫描与索引。会话废弃、外部共享结束和崩溃残留需有可操作的回收规则。

出口：异常文件不会错误进入可安装状态；原件不变；安装 / 分享权限往返可恢复；真实设备证明链路可用。

### 阶段 D：完整首版

建议按下面顺序交付，每一步可独立评审：

1. 新工具入口、主题、路由与独立依赖；已有功能回归。
2. 单文件读取、候选与包信息解析、详情、异常文件提示。
3. 副本生成、命名冲突、另存、系统安装与结果状态。
4. QQ / 微信外部入口、临时授权与冷 / 热启动恢复。
5. 来源管理、快速 / 扩大查找、索引、搜索与分类。
6. 首页最近、全部最近面板、副本预算与回收、另存、取消与进程中断恢复。
7. 端到端验收、权限说明、帮助文案和发布检查。

阶段 C 形成的链路在 D 中复用，不再独立重写一套。先验证文件可用，再增加扫描入口，避免做完大列表后才发现主要来源读不到。

### 阶段 E：验证与发布

本机按用户此前要求执行适合现有环境的静态检查和可运行的领域测试；Android 构建、URI / 权限集成、系统安装和触摸体验在具备环境的电脑及真机完成，分别记录证据。

重点覆盖候选匹配、命名、状态机、取消、不完整副本、同名文件、安装未知结果及权限撤回。不能用纯 JVM 测试替代手机访问能力验证。

正式发布前检查合并 Manifest、新增权限说明、测试 / 正式版入口区分、升级保留原有工具数据以及三种主题。文件快找独立发布范围和已知限制如实列入更新说明。

新增轻量化与离线验收：同构建条件的APK增量、首次结果与准备耗时、副本预算和大包例外、最近记录上限、飞行模式下已下载本地文件流程。竞品公开资料不是本项目的性能或兼容性证据。

## 6. 评审结论与剩余决策

**可以进入可达性验证和通用页面原型准备；尚不能把“自动扫描 QQ / 微信全部文件”视作已经确认的开发规格。**

已确认：设备为红米 K60，主要来源为 QQ / 微信；现有工程支持独立新增工具的结构。

本方案建议：首版聚焦 APK，附带通用文件搜索；采用查找、外部打开、手动选择三个入口；保留原件；扩大访问按用户操作选择；近期不做分包安装和批量安装。

正式功能开发前需落实：当前系统与软件版本、真实文件可达性、实际异常命名样本、安装结果获取方式、交付占用结束依据、扫描和解析资源阈值；能力验证程序不受此阶段限制。如分发渠道改变，需再次确认权限范围。上述缺口不阻塞当前文档入库和原型准备，但不能由模拟原型自动视为已解决。
