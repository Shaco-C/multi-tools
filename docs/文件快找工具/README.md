# 文件快找工具 · 产品设计包

设计日期：2026-10-29；最近评审：2026-10-30（复核版 0.3）

状态：文档复核完成，可进入可达性验证与通用页面原型准备；原型验收、真机验证和正式功能开发尚未完成。

代码基线：`multi-tools`，`main`，`8f9a6f7`（v1.2.0）。

这个工具解决两个连续的问题：聊天接收的文件不好找，以及安装包变成 `.apk.1` 等名称后不方便安装。建议名称为“文件快找”，工具箱入口说明为“找安装包和文档，处理异常后缀”。

## 已确认与设计假设

- 用户使用红米 K60，常用 QQ 和微信传输文件。
- 用户希望找到普通安装包和 `.apk.1` 等异常名称的安装包，同时考虑查找其他文件。
- 用户进一步明确：在 QQ 点击 `.apk.1` 的“用其他软件打开”时，希望能直接选择“随身工具箱”，由本工具接收并进入安装流程，省去当前依赖额外浏览器的步骤。这是首版必须优先验证的入口。
- 用户明确产品方向：离线、便捷、边界清晰、简单、好用、体积小。本轮据此减少页面与常驻操作，副本采用短期暂存策略；具体交互与预算仍待验收。
- 用户当前要求再次核查设计并将文档推送远程仓库；本文的优先级、界面和处理规则仍需后续原型与真机验收，提交文档不等于实现功能。
- 手机当前 Android、MIUI / HyperOS、QQ、微信版本尚未确认；不能根据机型推断当前系统，也不能承诺固定聊天目录可访问。
- 当前项目通过 GitHub Releases 分发 APK，本轮按这一已有渠道设计首版；其他应用商店的能力和权限策略需单独确认。

## 推荐决策

1. 查找、识别、生成正确后缀副本、请求系统安装形成完整流程。
2. 首版聚焦 APK，同时提供可访问范围内的通用文件名搜索；点击搜索即可切换安装包 / 全部，首次查文档无需先扫 APK。统一登记轻量元信息，筛选不改变扫描覆盖口径。
3. 同时设计“在工具中查找”“从聊天打开”“系统选择文件”三个入口；优先验证 QQ 的“用其他软件打开 → 随身工具箱”，必须覆盖外部打开，不能只支持分享。
4. 普通模式可使用选定文件和允许授权的目录；按需提供扩大查找范围的能力。拒绝广泛访问权限后仍可使用其他入口。
5. 扫描不改文件；处理异常后缀时保留原件。识别为 APK 不代表已通过安全检测，也不保证系统一定允许安装。
6. 采用单首页，内嵌最近使用，不设置底部页签；“查找安装包”“选择文件”为主要入口，管理收于右上角。已识别支持的 APK 统一使用“安装”按钮，自动处理异常文件名。
7. 下一步先准备最小原生能力验证与通用页面原型；QQ直接打开的三关、交付生命周期经真机验证且原型验收通过后，进入正式功能开发。替代导入方式不能算QQ指定入口通过。
8. 以包体增量、运行负担和副本占用共同衡量“小”。暂存保留期限与空间预算、最近记录条数见04；用户需长期保留的文件主动另存。
9. 单次处理一个文件，外部新请求不覆盖在途文件或误用安装回执。安装结果、文件保护独立管理，当前详情与交付中的副本受保护，未知状态有明确管理出口。
