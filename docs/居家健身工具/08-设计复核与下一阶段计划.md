## 1. 阶段判断

**建议进入下一阶段：交互原型与内容小样验证。** 核心需求、页面结构和训练闭环已足以开展验证，不必继续无边界增加功能。

**尚未达到直接铺开完整Android功能开发和250动作批量制作的条件。** 原因是内容小样、可点击交互、媒体体积与备份恢复方案仍缺实物验证；本轮也发现了几处会导致实现分歧的规则缺口，已在原文补齐。

阶段判断分开记录：

| 阶段 | 结论 | 依据 |

| 需求整理 → 原型与小样 | 可以推进 | 动作库、日程、逐组记录、统计、自建与备份的首版范围明确；本轮规则修订见下表 |

## 3. 保留的验证缺口

### 3.1 内容来源尚未形成可发布的素材包

已有来源路径和许可研究，但没有逐动作闭环证明“具体变式对应正确、这张图能采用、中文可用、手机可辨认”。wger实时API及全部媒体覆盖也未实测。下一阶段必须产出实际样本和逐资源台账，不能只再列一批网址。

本轮再次核对了 [RepDB数据/图片许可](https://raw.githubusercontent.com/RepDB/exercise-dataset/main/LICENSE-DATA.md)：它区分应用内使用与数据集再分发，也限制图片用于生成式AI参考。因此公开仓库的构建资料、受限原包和用户可导出的备份必须分别设计，不能“有图片就全部提交Git”。许可明确仍不等于教学准确。

### 3.2 恢复提示缺少个人负荷，仍只能提供一般参考

保留06的边界，不增加固定部位恢复表。此次复查的 [Mayo Clinic指导](https://www.mayoclinic.org/healthy-lifestyle/fitness/in-depth/weight-training/art-20045842) 仍建议避免连续两天训练同一肌群；这不支持给具体用户计算恢复百分比或确定恢复完成时刻。

原型要验证：仅日期补记降级、辅助参与标注、同一次训练不反复提醒，以及无提示不表示没有恢复需求。更细的人体区域提醒以审校后的肌群映射为前提，不从“腿部”一个标签猜测所有细分肌肉。

### 3.3 首页堆叠信息是否影响记组，尚未验证

时间轴、两张卡、恢复区和动作列表同时存在，常规手机可能首屏看不到主要按钮；5—7列同时显示两个肌群标签也可能过窄。下一阶段允许用可折叠摘要、“继续训练”定位、减少可视天数和弹性卡片高度调整，但保留连续日期、双卡含义和清楚组数。

需要检查长动作名、双图、横屏、大字体和读屏。文字线框尺寸不是已通过的真机UI规范。

### 3.4 备份与媒体恢复需要独立的技术方案

当前 `BackupContributor` 仅处理JSON，数据库事务也不能独自保证图片文件同时恢复成功。正式开发前应选定健身工具的媒体包格式，说明临时校验、资源引用、切换失败回退、启动时中断恢复和存储空间不足的行为。

首版恢复明确采用“预检后替换健身数据”，不顺带设计多端合并。方案需处理损坏/缺失图片、不支持版本、重复导入，以及归档/撤销/实际值/时区快照的完整保留；不能只验证JSON能解析。

## 4. 下一阶段具体做什么

阶段名称：**交互原型与内容小样验证**。本阶段结束应能实际点击流程、打开真实小样、核对统计，并给出开发范围。当前任务只完成复核和安排，没有在本轮开始制作原型或图片。

| 顺序/工作包 | 具体工作 | 应交付的材料 | 完成标准 |
| --- | --- | --- | --- |
| W01 规则与内容字典 | 固定动作ID、统计主部位、教学肌群、默认/允许用途、器械必需条件、次/秒与每侧口径；补目标输入和日期范围边界 | 数据字典、内容条目模板、典型样例数据 | 同一动作在建计划、教学、首页和统计中没有不同解释；空值和未知不被补造成事实 |
| W02 内容小样 | 12个核心动作＋4个边界样例，精确匹配素材或原创；制作统一正背肌肉图与关键帧，整理中文和署名 | 16行样本状态表、完整样本内容包、来源/修改/审核台账 | 每个样本的图文和用途可解释、静态教学可离线查看；缺项明确且有解决路径，正式使用前完成对应审核 |
| W03 可点击原型 | 首页日期轴、分类/列表/详情、建计划、训练计组、统计；补自建动作和备份预览/失败等关键分支 | 本地可点击原型、页面状态清单、交互走查记录 | 能按下方六个场景走通；查看教学与记组分开，历史选择与今日卡不混淆 |
| W04 统计与状态样例 | 复用06的手算例，增加多计划、归档、重加、撤销重记、单侧缺填和用途混合 | 输入记录与预期输出对照表 | 组数可对账、天次去重、未填次数不伪造；原型展示与预期一致 |
| W05 媒体与备份可行性设计 | 选媒体格式和尺寸、测小样实际文件大小，估算完整包；对照现有备份接口设计媒体恢复 | 媒体测量表、体积预算建议、备份恢复状态/失败处理方案、待工程验证列表 | 分清已测文件体积与未测APK/解码性能；未解决的恢复路径不能当作已支持 |
| W06 阶段评审与范围冻结 | 对照250候选评估有效覆盖和制作成本，明确首版功能与内容承诺 | 首版范围清单、部位×器械覆盖矩阵、缺口/排除项、开发任务拆分 | 不把12或16个小样冒充大多数常用动作；明确哪些进入首版、哪些后续 |

建议先完成W01的基本字段，再用同一套数据推进W02/W03/W04，最后合并W05/W06结论。小样失败可以更换来源或重做某个动作，不必重写全部功能设计。

### 4.1 六个必须实际走通的场景

1. **初次使用**：无计划进入 → 找胸部动作 → 查看双图和详情 → 回到列表；无计划可新建，不会得到无归属的完成记录。
2. **用户原始示例**：建两日多部位计划 → 配动作和目标 → 保存 → 今日记录 → 看教学返回 → 撤销和继续 → 在统计中追溯。
3. **计划覆盖与编辑**：选胸肩却仅有胸部动作 → 明确缺口 → 补齐；训练后移除再加入 → 恢复原进度；取消所有剩余安排 → 历史仍在。
4. **日期与多计划**：训练/休息/未安排连续展示 → 同日两个计划 → 跨午夜继续原日 → 补记和归档 → 今日任务、历史和统计各自正确。
5. **用途与计量**：纯有氧日、仅热身日、拉伸每侧计时、左右实际值缺一侧 → 组/段、连续天数及覆盖率正确；自建非力量动作不被迫选肌肉。
6. **异常与恢复**：模拟保存失败、素材缺失、备份缺图/损坏、恢复中断 → 原进度和原资料不因失败被假装成功；原型模拟与真实持久化验收分别标注。

## 5. 何时可以开始正式开发

进入正式开发的建议条件如下。当前除规则修订外，其余尚待下一阶段产物证明：

- 首版导航、计量、计划主部位、归档/撤销/重加规则在原型中无冲突；关键问题有结论，不能留下多个互斥默认。
- 16个样本覆盖各用途和计量边界，确认可行的取材/原创与审核路线；至少能展示完整静态教学，缺动图有回退。
- 统计样例可手算对账，数据字典能够表达快照、撤销、实际值空缺、时间来源和媒体引用。
- 已确定媒体显示方案、预算判断方法，以及备份包/失败恢复设计；Android专项验证列为明确开发任务。
- 首版正式内容目标、部位×器械覆盖、责任人及未完成项有清单。250候选不必全部先制作完才写计组功能，但交付范围不能仅写“尽量丰富”。
- 内容与功能可以随后按模块推进；发布前仍须完成约定内容数量、有效覆盖和真实设备验收。

达到这些条件后，建议开发顺序为：模块入口与只读动作内容 → 计划与草稿 → 可靠记组/撤销/历史 → 首页时间轴及统计 → 自建媒体/备份恢复 → 集成与真机验收。内容制作持续推进，避免功能写完后才发现素材来源不适用。
