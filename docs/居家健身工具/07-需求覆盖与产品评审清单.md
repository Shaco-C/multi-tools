## 2. 本轮补齐的关键细节

1. **安排与实际分离。** 选了胸部或建立计划不会增加训练统计；修改、取消安排也不能抹掉已训练事实。
2. **计组与计次分离。** 一击只确认一组；想看重复次数时可补实际值，不用目标乘积冒充实际完成。
3. **同日多计划不混记录。** 执行分别保存；统计天数按自然日去重，组数按有效记录相加。
4. **复合动作不重复累加组数。** 单一统计主归属与多肌群教学映射分开，辅助参与仍用于内容和恢复参考。
5. **热身、有氧、拉伸各有口径。** 有氧可以计训练日；热身拉伸单独记录。首页能处理纯有氧日，混合日按组/段分别显示。
6. **连续天数不鼓励忽略休息。** 今天没练可显示截至昨天的值；没有训练的休息日会中断自然日连续，不给负面惩罚文案。
7. **补记、跨午夜、时区都有归属。** 统计看训练日期；恢复参考看可信时刻；补记操作时间不当成实际训练时刻。
8. **正常组间训练不反复弹恢复提示。** 提醒用于当天开始前和跨日安排，不在刚完成第一组时要求隔天再练。
9. **历史内容有快照。** 改动作名称、肌群、用途、目标、停用和归档都不能静默重写旧统计。
10. **媒体也纳入备份边界。** 用户图片与数据共同恢复；内置媒体按ID/版本引用，已有JSON备份接口并未天然支持图片包。
11. **图片获取可执行。** 从实际JSON字段和来源ID取文件；缺图、缺帧、变式不符或许可不清时有回退路径，不按名称猜图。
12. **数量与质量分别验收。** 250是候选规模；正式可用需图文齐全、器械条件完整、来源可追溯并审校通过。

## 3. 从三种身份检视

| 视角 | 最关心的问题 | 当前应对 | 还需验证 |
| --- | --- | --- | --- |
| 实际用户 | 做到第几组能否一眼看懂，误点能否改 | 大数字、下一组按钮、最近时间、持续撤销入口 | 单手/疲劳状态操作、长列表继续训练定位 |
| 实际用户 | 不认识动作或器械缺少怎么办 | 双图、完整教学、器械筛选、已审替代动作 | 图是否足够清楚，文字是否易懂 |
| 实际用户 | 今天练什么、哪天没安排 | 连续日轴、今日部位、明确休息/未安排 | 一屏可视天数、多部位及大字体布局 |
| 产品经理 | 功能多但主流程不能变复杂 | 记组始终一击；统计与管理独立；实际值可选 | 首次建计划的步数、草稿恢复和批量配置 |
| 产品经理 | 统计是否可解释、建议是否可信 | 指标字典、明细可追溯、恢复参考分级 | 手算数据、补记撤销与跨日交互 |
| 甲方 | “大量内置动作”能否验收 | 250候选覆盖矩阵＋逐动作内容发布门槛 | 12小样通过后确定首版有效数量及缺口 |
| 甲方 | 能否离线使用，后续是否维护得动 | 静态图随包、稳定ID、来源台账、增量审校 | 包体积、版权与更新链、真机性能 |

## 4. 仍需定案的事项与合理默认

这些事项不阻止继续做文档和小样设计，实施前再结合样本和成本确定；不是要求用户现在逐条回答。

| 待定事项 | 当前默认建议 | 如何定案 |
| --- | --- | --- |
| 正式名称和工具图标 | 暂名居家健身，图标与工具箱一致 | 原型时比较，不先生成大量装饰素材 |
| 首版正式动作数 | 以250候选为建设池，确保主要居家部位和器械覆盖 | 输出逐条“通过/待补/排除”及覆盖缺口，由范围评审决定 |
| 媒体来源比例与预算 | 开放资料＋统一肌肉图＋必要原创，动图为增强 | 12小样比较质量、成本、授权和离线体积 |
| 可接受的安装包增量 | 首版静态教学随应用内置 | 先量12样例，再按真实均值估算全库；不凭估算直接承诺 |
| 内容审核责任 | 明确负责动作、肌群、中文与许可的人 | 小样阶段确认责任与记录模板 |
| 实际次数补填 | 首版组明细可选，默认一击只计组 | 原型验证填写和统计覆盖率是否容易理解 |
| 首页卡片尺寸与时间轴天数 | 两列近方形、约5–7天可见，字号优先 | 以现有主题的小屏/大字体原型验证 |
| 恢复建议的措辞 | 同肌群训练留间隔，48小时只作一般筛查参考 | 内容审核确认短文案；不扩展成个体恢复预测 |

## 5. 后续编码落点与现有规范

本项目是原生 Android 工具箱，不属于工作区的 Java 运输微服务。本次确认仓库 `multi-tools`、分支 `main`，没有修改应用代码。

| 事项 | 后续遵循的现有方式 |
| --- | --- |
| 正式工程 | `android_app`，Kotlin/Jetpack Compose/Material3/Room；原型目录不能代替正式Android实现 |
| 新工具模块 | 建议 `android_app/feature/fitness`；通过现有 `ToolModule` 加入工具注册，app只组装入口与依赖 |
| 依赖方向 | app → feature → core；健身业务不直接依赖电费/饮食工具内部实现 |
| 职责分层 | presentation 管页面状态和交互，domain 管规则，data 管数据库/内容/媒体；不在Composable里执行导入、统计查询或磁盘写入 |
| 通用样式 | 优先复用 `core/designsystem` 主题与现有工具页面模式；已有样式未抽成组件的部分先保持一致，不顺带全项目重构 |
| 视觉基准 | 三套浅色主题、海军蓝主卡、薄荷青操作；约18dp边距、920dp最大内容宽度、20–21dp卡片圆角，计组按钮可放大至56dp |
| 内置内容 | 建议 `feature/fitness/src/main/assets/fitness`；可公开母版/台账建议仓库 `content/fitness` |
| 用户内容 | 独立本地数据库与应用私有图片目录，不覆盖内置资源 |
| 备份 | 复用逐工具隔离与预检思想，另外设计数据和媒体的共同恢复；不声称现有JSON契约已解决图片备份 |
| 编码风格 | 服从相邻模块Kotlin风格、已有工具和状态模式；当前未发现统一ktlint/detekt配置，不把新文档规则冒称为既有强制检查 |
| 验证 | 规则和聚合测试、Room持久化、Compose交互及真机媒体性能分别验证；服务端PostgreSQL/Druid规则不套用于此Room工程 |

现有代码参考点：`core/navigation/.../ToolModule.kt`、`core/designsystem/.../ToolboxTheme.kt` 与 `ToolboxColors.kt`、`core/backup/.../BackupContributor.kt`，以及 `feature/electricity`、`feature/diet` 的入口和分层。详细实现文件与DDL在进入开发阶段后确定，不在产品文档中提前锁死。

## 6. 首版之后可以增加的功能

本表是后续版本候选，不是紧接本次复核就要实施的任务。下一阶段只验证既定首版的交互与内容，具体见08，避免“下一步”被误读为继续扩张功能。

| 优先级 | 功能 | 理由与边界 |
| --- | --- | --- |
| 首版后优先 | 组间休息倒计时 | 紧贴记组场景，但要区分后台计时、通知和肌群隔日恢复 |
| 首版后优先 | 收藏/最近动作、复制周计划 | 减少重复选动作；不改变历史统计 |
| 首版后优先 | 临时训练快捷入口 | 无计划时快速选动作和目标，内部仍生成明确日期的安排，避免游离记录 |
| 首版后优先 | 按条件挑选动作 | 用户已提出的后续需求，先有可靠动作池再做随机与替换 |
| 后续 | 重量、主观强度、个人备注 | 为容量或个性化建议提供真实输入，不靠目标次数猜测 |
| 后续 | 训练提醒、可选常亮、月历与统计导出 | 结合实际使用频率决定，不阻断首版闭环 |
| 独立评估 | 云同步、摄像头自动识别、AI姿势评分 | 涉及新的数据、权限、成本与准确性问题，本轮不纳入 |

## 7. 建议的下一次评审材料

1. 用12个核心动作＋4个边界样例做内容小样：能在手机尺寸下查看双图、步骤、肌群和中文说明，并带来源台账。4个补充样例覆盖前臂/每侧计时、有氧、热身、拉伸，不增加250个候选总数。
2. 做可点击的首页时间轴、动作列表/详情、建计划、记组、统计六类核心流程原型，沿用现有工具箱主题。
3. 使用06的可手算样例走通统计，再补充仅有氧、每侧缺填、跨午夜、补记撤销和多个计划的情况。
4. 依据小样测量媒体体积与显示质量，确定正式动作覆盖、素材组合和分阶段交付范围，再进入应用开发。

本轮交付的是完整的产品评审材料与可执行内容建设方案。核心闭环和本轮新增需求都有对应规则；剩余工作主要是内容实物验证、交互验证和范围定案，不能用继续堆砌功能代替这些验证。
